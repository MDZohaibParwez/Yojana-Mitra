# Decisions

Decisions taken while building, so they can be reviewed later. Newest phase last.

## Phase 1 – Monorepo & database

1. **TypeScript source packages, no build step for libraries.** `packages/*` export `src/index.ts` directly. Apps that deploy as serverless functions (`apps/mcp`, `apps/api`, `apps/whatsapp`) bundle everything with esbuild (`tsup`) so Vercel never has to resolve workspace TypeScript. Next.js uses `transpilePackages`.
2. **Drizzle + postgres.js**, `prepare: false` so it works behind Neon/Supabase transaction poolers. Migrations are generated by drizzle-kit (`packages/db/migrations`), plus one hand-written migration for search indexes and a CHECK constraint (approved rule ⇒ reviewer recorded).
3. **Scheme text storage.** `schemes` keeps the English content + `name` as JSON per language (official names). Other languages live in `scheme_translations` with their own `review_status`; unapproved translations are never served – core falls back to English.
4. **Two review gates.** A scheme is visible only when `schemes.review_status = 'approved'` **and** `last_verified_at` is set **and** it has an approved eligibility rule. Rules are versioned; a new version is always `pending`.
5. **Search.** Postgres `simple` FTS (language-agnostic) + an ILIKE fallback, because the default Postgres parser splits Indic words at vowel signs. pgvector (`vector(1024)`, HNSW cosine) for cross-lingual semantic search when an embeddings endpoint is configured. 1024 dims fits common multilingual models (bge-m3, multilingual-e5-large).
6. **Chat session state** is stored in `chat_sessions` keyed by an HMAC of the phone number (never the raw number), with `expires_at`.
7. **`usage_events`** has only channel, tool, state, lang, timestamp – the schema physically cannot hold personal data.

## Phase 2 – Eligibility engine

8. **Profile fields.** Beyond the required ones, added `isIncomeTaxPayer`, `isPregnantOrLactating`, `hasPuccaHouse` and `disabilityPercent` because major central schemes (PM-KISAN, APY, PMMVY, PMAY, IGNDPS) hinge on them. Land is in **hectares** (official unit); the chat parser converts acres/bigha-free inputs ("2 acre" → 0.81 ha).
9. **Three-valued logic.** Each node evaluates to true / false / unknown. AND: any false ⇒ false, else any unknown ⇒ unknown. OR: any true ⇒ true, else any unknown ⇒ unknown. NOT flips true/false and keeps unknown. `unknown` at the root ⇒ `"maybe"` with `missing` fields in a fixed, user-friendly question order.
10. **Education is ordinal** (`none < primary < secondary < higher_secondary < diploma < graduate < postgraduate`) so rules can say `educationLevel gte secondary`.
11. **Ranking** = match strength (0–100, a confirmed match always beats a maybe) + benefit size (log scale, ≤20) + deadline proximity (≤15) + query relevance (≤30).
12. **Income** in rules is annual *family* income. Where a scheme uses monthly individual income (PM-SYM ₹15,000/month), the rule converts (₹1.8 lakh/yr) and carries a `note` quoting the official criterion.

## Phase 3 – Data

13. **Curated seed data is treated like LLM output.** The 31 central schemes in `data/schemes/central.json` were written by the coding agent from official scheme guidelines it knows; they have **not** been checked against live portals from this sandbox (myscheme.gov.in is blocked by the build sandbox's network policy). `pnpm db:seed` loads them as **pending**. A human must approve them (`pnpm review`) – approval stamps `last_verified_at`. `pnpm db:seed --dev-approve` exists for local development only and refuses to run with `NODE_ENV=production`.
14. **Claude for rule extraction / translation** uses `claude-opus-5-5` (override with `INGEST_MODEL`) via structured outputs. The recursive rule tree is returned as a JSON string inside a fixed wrapper and validated locally with the same zod schema the engine uses; invalid output is retried once with the validation error, then rejected. Server-side refusal fallbacks (`fallbacks: "default"`) are enabled.
15. **myScheme importer uses only public pages + sitemap**, not the internal search API (which needs a key embedded in their web app). All importers ship disabled until ToS review (see DATA_SOURCES.md).
16. **Re-verification semantics.** Dead link or changed source page ⇒ scheme back to `pending` (hidden). Unchanged page of an approved scheme ⇒ `last_verified_at` refreshed, because the content still matches what a human approved.
17. **Top-schemes stat** uses a separate aggregated `scheme_views(scheme_id, day, views)` counter so `usage_events` stays exactly channel/tool/state/lang/timestamp.

## Phase 4–5 – API & MCP

18. **Hono** for the API, MCP and WhatsApp services: one framework that runs on Node, Vercel functions and tests (`app.request`) without a server.
19. **Rate limiting** is an in-memory fixed window keyed by `sha256(ip + day + secret)` — raw IPs are never stored. On serverless each instance counts separately; add a Vercel Firewall rate-limit rule for a hard global cap.
20. **MCP runs stateless** (`sessionIdGenerator: undefined`, JSON responses): a fresh server+transport per POST, so it scales on Vercel and holds no user state. `GET`/`DELETE /mcp` return 405.
21. **MCP tool results** return both `structuredContent` and the same JSON as text (for clients that only read text). Tool failures come back as `isError: true` with a coded, actionable message (e.g. `not_found: … use find_schemes`) instead of protocol errors.
22. **No auth on public tools** (per spec). The MCP server therefore needs no OAuth for the directory; only `report_issue` writes, and it is rate-limited, redacted and rejects identifiers.
23. **Deploy bundles**: `tsup` bundles each Vercel function into `api/index.js` with all dependencies inlined.

## Phase 6 – States & UTs

24. **All 36 States/UTs are registered** as sources (`registry.ts`) and in the profile (`STATES`), but full state coverage is designed to come from myScheme ingestion (which lists state schemes with their state) plus per-portal importers. Only 16 flagship state schemes in 13 states are hand-curated (`data/schemes/states/*.json`), because hand-writing rules for thousands of schemes without being able to read the portals would mean guessing. `pnpm --filter @ym/ingest coverage` reports per-state counts.
25. **State schemes always include `state eq <code>`** in their rule (enforced by a test), and `find_schemes` only loads central + the user's own state schemes.
26. **Amounts that change often** (Ladli Behna, Lakshmir Bhandar, Maiyan Samman, Orunodoi, Kanya Sumangala totals) are written as "as currently notified" rather than a number I cannot verify; the reviewer should fill in the current figure.
